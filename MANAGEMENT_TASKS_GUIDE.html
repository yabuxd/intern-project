Task 1: Order Placement & Multi-Fulfillment (Dine-In vs Delivery)
MODULE: ORDERS & POS

Core Functionality: Allows customers or staff to assemble orders with dynamic line items, select fulfillment mode (dine_in with table association or delivery with recipient coordinates/phone), select payment method (cash or chapa), and atomically calculate totals and item snapshot prices inside a database transaction.

1. Backend Code Implementation & Functionality

  • server/app/Http/Controllers/Api/OrderController.php (store: lines 143-260)

    Executes within DB::transaction(). Validates that all menu item IDs are currently available (is_available: true). Creates the header Order record, inserts OrderItem rows snapshotting unit_price and line_total, and sets order total. If Chapa online payment is selected, it dispatches an initialize transaction request to ChapaPaymentService and returns the generated checkout_url.

  • server/app/Http/Requests/StoreOrderRequest.php

    Enforces payload validation: items array (min: 1), items.*.menu_item_id (exists in menu_items), items.*.quantity (integer, min: 1), conditional requirement for delivery_address and delivery_phone when fulfillment_type === 'delivery', and table assignment validation for dine_in.

  • server/app/Models/Order.php (lines 180-237)

    Defines status progression and transition guards via allowedNextStatuses() and canUserTransition(). 

// server/app/Http/Controllers/Api/OrderController.php: store() snippet
$order = DB::transaction(function () use ($validated, $user, $fulfillment, $paymentMethod) {
    $menuItemIds = collect($validated['items'])->pluck('menu_item_id')->unique()->all();
    $menuItems = MenuItem::query()->whereIn('id', $menuItemIds)->where('is_available', true)->get()->keyBy('id');
    
    if ($menuItems->count() !== count($menuItemIds)) {
        throw ValidationException::withMessages(['items' => ['One or more menu items are unavailable.']]);
    }

    $order = Order::query()->create([
        'user_id' => $user->id,
        'table_id' => $fulfillment === Order::FULFILLMENT_DELIVERY ? null : ($validated['table_id'] ?? null),
        'fulfillment_type' => $fulfillment,
        'delivery_address' => $fulfillment === Order::FULFILLMENT_DELIVERY ? trim($validated['delivery_address']) : null,
        'delivery_phone' => $fulfillment === Order::FULFILLMENT_DELIVERY ? trim($validated['delivery_phone']) : null,
        'status' => Order::STATUS_PENDING,
        'payment_method' => $paymentMethod,
        'payment_status' => $paymentMethod === Order::PAYMENT_METHOD_CHAPA ? Order::PAYMENT_PENDING : Order::PAYMENT_NOT_REQUIRED,
    ]);

    $total = 0;
    foreach ($validated['items'] as $line) {
        $item = $menuItems->get($line['menu_item_id']);
        $lineTotal = round((float) $item->price * $line['quantity'], 2);
        OrderItem::query()->create([
            'order_id' => $order->id, 'menu_item_id' => $item->id,
            'quantity' => $line['quantity'], 'unit_price' => $item->price, 'line_total' => $lineTotal,
        ]);
        $total += $lineTotal;
    }
    $order->update(['total' => round($total, 2)]);
    return $order;
});

Task 2: Kitchen Queue & Live Expediting Pipeline
MODULE: KITCHEN OPERATIONS

Core Functionality: Provides kitchen chefs and expediting staff with an active, real-time ticket display. Filters out unapproved online orders, groups active preparation stages (pending, accepted, preparing, ready), and supports one-click status transitions with Supabase Realtime synchronization and 5-second polling fallback.

  • server/app/Http/Controllers/Api/OrderController.php (queue: lines 52-89)

    Requires can_view_all_orders authorization. Applies scopePaymentSettled() to guarantee only confirmed cash orders or cashier-approved Chapa orders reach the kitchen. Uses cursor pagination (KeysetPaginator) ascending by ID for FIFO queue ordering.

  • server/app/Models/Order.php (scopePaymentSettled: lines 307-318)

    Enforces strict segregation: Cash orders are immediately visible (payment_status: not_required), while Chapa orders require both payment_status: paid AND cashier_approved_at IS NOT NULL.

2. Frontend Code Implementation & Functionality

  • client/src/pages/OrderQueuePage.tsx

    Displays active kitchen tickets organized by status columns with badge indicators, table/delivery tags, customer notes, item quantities, and action buttons ("Start Preparing", "Mark Ready", "Mark Served").

  • client/src/hooks/useOrdersRealtime.ts

    Subscribes to the Supabase Realtime WebSocket channel on table orders. Triggers React Query cache invalidation (queryClient.invalidateQueries) immediately upon receiving Postgres change events. Falls back to a 5000ms polling interval if WebSocket disconnects or when running against local SQLite.

Task 5: Floor Tables & Conflict-Free Table Reservations
MODULE: FLOOR & RESERVATIONS

Core Functionality: Comprehensive table inventory and booking system. Manages restaurant floor tables (capacity, name, status: free, reserved, occupied) and guarantees conflict-free table reservations using pessimistic row-level locking and overlapping timeslot assertion algorithms.

1. Backend Code Implementation & Functionality

  • server/app/Http/Controllers/Api/TableController.php

    Provides public table listing with HTTP ETag caching and 304 Not Modified negotiation. Offers staff CRUD operations (store, update, destroy) gated by can_manage_tables.

  • server/app/Http/Controllers/Api/ReservationController.php (store: lines 55-84)

    Executes inside a database transaction. Locks the target table row with RestaurantTable::lockForUpdate() to prevent race conditions during simultaneous booking attempts.

  • server/app/Services/ReservationAvailabilityService.php

    Asserts party size does not exceed table capacity and executes overlapping window query: starts_at < $endsAt AND ends_at > $startsAt AND status = 'confirmed'. Throws ValidationException if conflict detected. 

// server/app/Services/ReservationAvailabilityService.php: assertAvailable()
public function assertAvailable(RestaurantTable $table, int $partySize, CarbonInterface $startsAt, CarbonInterface $endsAt): void
{
    if ($table->capacity !== null && $partySize > $table->capacity) {
        throw ValidationException::withMessages(['party_size' => ["Table only seats {$table->capacity} guests."]]);
    }

    $conflict = Reservation::query()
        ->where('table_id', $table->id)
        ->where('status', Reservation::STATUS_CONFIRMED)
        ->where('starts_at', '<', $endsAt)
        ->where('ends_at', '>', $startsAt)
        ->exists();

    if ($conflict) {
        throw ValidationException::withMessages(['table_id' => ['Table is already reserved for this time window.']]);
    }
}

  • client/src/pages/ReservationsPage.tsx

    Reservation log showing booking timeline, start/end times, guest party size, contact notes, and cancellation triggers.

Allows administrators to provision new user accounts (synced with Supabase Auth), assign roles (admin, manager, cashier, kitchen, host, delivery, customer), and customize permissions assigned to each role through a live matrix grid.

1. Backend Code Implementation & Functionality

  • server/app/Http/Controllers/Api/UserPermissionController.php

    Gated by can_manage_permissions.
    index(): Keyset-paginated list of users with assigned roles and computed permissions.
    store(): Provisions user account in Supabase via SupabaseAdminUserService, inserts local users record, and syncs initial roles.
    updateUserRoles(): Updates user's role assignments and clears their auth cache.
    updateRolePermissions(): Syncs permission IDs for a specific role and flushes auth caches for all users holding that role.

  • server/app/Models/User.php (authProfile: lines 57-82)

    Calculates user's effective permissions by flattening all assigned roles' permissions and always adding can_place_order. Result is cached in RAM and Redis/File store via ApiCacheService::rememberUserAuth.

  • server/app/Providers/AppServiceProvider.php (boot: lines 57-65)

    Registers Laravel authorization Gates dynamically for every permission in Permission::catalog().

Task 8: Executive Analytics, Revenue Auditing & Operational KPIs
MODULE: ANALYTICS & AUDIT

Core Functionality: Executive business intelligence dashboard aggregating restaurant metrics across customizable date ranges. Computes total sales, paid revenue in ETB, average order value (AOV), top 8 best-selling dishes with revenue attribution, delivery dispatch health, floor table occupancy rates, and pending cashier queue totals.

1. Backend Code Implementation & Functionality

  • server/app/Http/Controllers/Api/AdminDashboardController.php

    Accepts from and to ISO timestamp query parameters (defaults to trailing 7 days). Gated by can_manage_permissions. Caches aggregated results in ApiCacheService::rememberAdminDashboard using SHA256 hashed date-range keys.

  • Calculated Analytics Aggregations:
    • Orders & Revenue: Total volume, status distribution, paid order count, paid revenue sum, average order value (AOV).
    • Top Selling Dishes: Joins order_items with orders, aggregates quantity_sold and revenue, filters out cancelled orders, and retrieves top 8 items.
    • Payment & Cashier Health: Number of Chapa orders awaiting cashier validation, uncollected cash order count.
    • Logistics: Active deliveries, unassigned delivery orders, completed deliveries.
    • Reservations: Confirmed, cancelled, and upcoming bookings count.
    • Floor Occupancy: Instant breakdown of tables by status (free, reserved, occupied).

2. Frontend Code Implementation & Functionality

  • client/src/pages/AdminDashboardPage.tsx

    Comprehensive executive dashboard with custom date-range picker presets (Today, 7 Days, 30 Days, Custom). Displays KPI summary cards, interactive revenue graphs, dish ranking tables, and operational alert counters with automatic prefetching via api.ts:prefetchAdminDashboard.
